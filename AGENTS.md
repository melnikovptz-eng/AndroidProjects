# Правила работы ИИ в репозитории

Перед любой задачей сначала открыть PROJECT_REGISTRY.md, затем соответствующую запись в WORKLOG.md. Это обязательная точка входа.

## Быстрый порядок
1. Определить проект по реестру: точный каталог, рабочую ветку, workflow, команду сборки и тип артефакта.
2. Прочитать только паспорт/ТЗ нужного проекта и связанные с задачей исходники. Не сканировать весь репозиторий, если реестр и журнал покрывают текущую область.
3. Сверить текущий HEAD с checkpoint в WORKLOG. Если SHA совпадает и задача не затрагивает другие файлы, использовать сохранённые сведения; при отличии SHA просмотреть только commits/diff после checkpoint и обновить журнал.
4. Перед изменением найти существующего владельца функции. Не создавать дубликаты классов, сервисов, очередей, хранилищ и workflow.
5. Выполнять одну законченную задачу/модуль за логический цикл. Статические проверки — сразу; интеграционные тесты и сборка — после завершения связанного блока.
6. После завершения обновить WORKLOG и при необходимости PROJECT_REGISTRY в том же рабочем цикле.

## Правило «последний рабочий APK/файл» — обязательно
Никогда не выбирать APK по одному имени файла, дате загрузки, номеру версии или расположению в папке.

Для ответа «дай последний рабочий APK»:
1. Уточнить проект по PROJECT_REGISTRY; если проект уже назван в запросе/контексте, не задавать вопрос повторно.
2. Проверить workflow, предназначенный именно для этого проекта.
3. Найти самый новый успешный run (conclusion=success) на зарегистрированной рабочей ветке.
4. Сопоставить head_sha run с текущим HEAD этой ветки.
5. Скачать/выдать артефакт именно из этого run и проверить его build manifest, package/application ID, вариант сборки и SHA-256, если manifest доступен.
6. Если SHA run не равен текущему HEAD, называть файл только «последняя успешная сборка старого коммита», а не «APK текущей версии». Если нужный артефакт не найден или run неуспешен — честно сообщить об этом и не подменять другим проектом.
7. Никогда не выдавать ZIP исходников за APK, APK другого проекта за нужный, debug за release или старый tracked APK за последний без проверки.
8. В ответе указывать проект, ветку, короткий source SHA, workflow run и вариант (debug/release). Если этих данных нет, статус — НЕ ПОДТВЕРЖДЕНО.

## Точность проекта
- Не переключать ветку и не менять каталог проекта без причины.
- Не переносить изменения одного проекта в другой.
- Не считать наличие класса/кнопки/ресурса доказательством готовности.
- Не заявлять о тестах, сборке или проверке устройства без результата, относящегося к конкретному SHA.
- Не удалять пользовательские данные, резервные копии, исходники и незавершённые изменения без явной необходимости.
- Для PMCA соблюдать PROJECT_CONTRACT.md и архитектурные документы; для Aeroclub — TECHNICAL_SPEC.md, MODULE_PASSPORTS.md и MODULE_ARCHITECTURE.md. Этот файл задаёт общий процесс, но не заменяет проектное ТЗ.

## Обновление журнала
В WORKLOG добавлять короткую запись: дата, проект, ветка, source SHA, что сделано, что проверено, что осталось, последний подтверждённый артефакт. Не переписывать старые записи и не утверждать, что непроверенная работа завершена.

## Приоритет
Точное соответствие проекту и проверяемость результата важнее скорости ответа. Скорость достигается повторным использованием реестра/журнала, локальными проверками и отказом от полного сканирования без необходимости.
