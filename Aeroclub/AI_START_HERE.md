# KD PILOT — инструкция быстрого входа для ИИ

> **KD PILOT** — пользовательское название проекта информера аэроклуба в этом репозитории. В GitHub он находится в каталоге `Aeroclub/`, рабочая ветка — `aeroclub-informer`. Если пользователь говорит «делай KD PILOT», «продолжай KD PILOT» или «вернёмся к KD PILOT», это означает продолжать именно этот проект, а не Copy Termix GPT, PMCA, VoiceWordDetector или другие приложения.

## 1. Обязательное начало каждой новой сессии

Не спрашивать пользователя заново, какой проект имеется в виду, если он назвал KD PILOT.

Прочитать документы в таком порядке:

1. Корневой `AGENTS.md` на ветке `main` — общие правила репозитория.
2. `PROJECT_REGISTRY.md` на `main` — каталог, ветка, workflow и контрольные точки проектов.
3. Соответствующую секцию `WORKLOG.md` на `main` — последние выполненные работы и подтверждённые проверки.
4. `Aeroclub/AGENTS.md` на ветке `aeroclub-informer`.
5. `Aeroclub/TASK_REGISTRY.md` — незакрытые задачи и критерии приёмки. Это первый проектный документ перед изменением кода.
6. `Aeroclub/SCREEN_MAP.md` — постоянные ID экранов и виджета.
7. `Aeroclub/TECHNICAL_SPEC.md`, `Aeroclub/MODULE_PASSPORTS.md`, `Aeroclub/MODULE_ARCHITECTURE.md` и относящиеся к текущей задаче документы.
8. Для любой задачи дизайна — `Aeroclub/design/README.md`, `Aeroclub/design/DESIGN_REFERENCE.md` и оригинал `Aeroclub/design/dezign.jpg`.

## 2. Как возобновлять работу без повторного полного аудита

- Получить текущий HEAD ветки `aeroclub-informer`.
- Сравнить его с checkpoint в `PROJECT_REGISTRY.md` и `WORKLOG.md`.
- Если SHA совпадает — использовать журнал и читать только файлы текущей задачи.
- Если SHA отличается — посмотреть commits/diff после checkpoint и обновить понимание состояния.
- Полный аудит выполнять только при изменении архитектуры, неизвестном состоянии, противоречиях в документации или прямой просьбе пользователя.
- Перед изменением найти существующего владельца функции. Не создавать дубликаты экранов, провайдеров виджета, хранилищ, сервисов и обработчиков.

## 3. Главная текущая задача

Сначала проверить верхнюю незакрытую задачу в `Aeroclub/TASK_REGISTRY.md`. По последней прочитанной записи приоритетный блокер — **AERO-011: новый домашний виджет W01 по оригинальному макету KD PILOT**.

Критически важно:

- W01 — домашний виджет Android.
- S01 — отдельный главный экран приложения с календарём полётов.
- W01 и S01 должны существовать параллельно; не подменять один другим.
- Источник истины для дизайна W01 — оригинал `Aeroclub/design/dezign.jpg`.
- Сначала изучить оригинал и текущий код, зафиксировать расхождения, только затем редактировать.
- Не объявлять визуальное совпадение, успешную сборку или проверку на телефоне без конкретного подтверждения.

## 4. Основные функции приложения

По проектной документации приложение включает:

- календарь полётов и карточки мероприятий;
- ответы участника «Я поеду» / «Я не поеду»;
- маршрут к месту полётов с подтверждением выезда;
- подготовку текста для Telegram/системного меню передачи;
- локальную административную панель для полётов, участников, сообщений и настроек;
- локальное хранение данных и обмен JSON-файлом полётов через Android Downloads;
- локальные напоминания о предстоящих полётах;
- домашний виджет W01, который должен соответствовать оригинальному макету.

Не приписывать приложению серверную синхронизацию, авторизацию, FCM или гарантированную доставку сообщений: считать их отсутствующими, пока код и инфраструктура не докажут обратное.

## 5. Реестр и журнал — обязательны

- `Aeroclub/TASK_REGISTRY.md` — реестр задач: требования, приоритеты, статусы, критерии приёмки. Закрытые записи не удалять.
- `Aeroclub/SCREEN_MAP.md` — постоянные ID экранов/виджета.
- Корневой `WORKLOG.md` — журнал фактически выполненных работ по проектам.
- Корневой `PROJECT_REGISTRY.md` — карта проектов и контрольные точки.

Новую задачу сначала записать в реестр, если её там ещё нет. После завершения логического блока добавить запись в WORKLOG и обновить статус задачи: commit SHA, что изменено, какие тесты прошли, CI run/source SHA, проверка на устройстве и что осталось.

Не переводить задачу в DONE только потому, что код написан или сборка прошла. Раздельно отмечать:
1. исходники изменены;
2. статические проверки/юнит-тесты пройдены;
3. CI-сборка успешна;
4. артефакт собран с нужного source SHA;
5. поведение проверено на реальном устройстве.

## 6. Правила изменений

- Работать только в `Aeroclub/` и ветке `aeroclub-informer`, если пользователь явно не поручил иное.
- Не менять другие проекты репозитория.
- Не удалять данные, исходные макеты и историю выполненных задач.
- Не перезаписывать оригинал дизайна.
- Не добавлять функции, которых нет в ТЗ.
- Не делать косметические правки наугад: каждое изменение UI должно иметь ссылку на эталон или зарегистрированный дефект.
- После изменения запускать подходящие тесты и сборку; для UI проверять скриншот и, где требуется, физическое устройство.
- В ответе сообщать только подтверждённые результаты и явно указывать оставшиеся проверки.

## 7. Формат записи о выполнении

`ID задачи | дата | ветка | source SHA | изменение | тесты | CI run | проверка устройства | остаток`

Если проверка не выполнялась, писать «НЕ ПРОВЕРЕНО», а не предполагать успех.
