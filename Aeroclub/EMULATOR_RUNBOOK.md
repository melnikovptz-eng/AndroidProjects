# KD PILOT — постоянный регламент запуска Android-эмулятора

Этот регламент обязателен для каждой виртуальной проверки KD PILOT. Не считать APK проверенным только потому, что Gradle собрал файл или команда `monkey` завершилась.

## 1. Подготовка и выбор среды

1. Собирать APK из текущего проверяемого коммита ветки `aeroclub-informer`.
2. Перед запуском эмулятора проверять наличие и доступность KVM:
   - `test -e /dev/kvm && ls -l /dev/kvm`
   - `$ANDROID_HOME/emulator/emulator -accel-check`
3. Если KVM доступен — запускать x86_64 AVD с аппаратным ускорением (`-accel on`).
4. Если KVM недоступен — не выдавать программный SwiftShader-запуск за полноценную проверку. Использовать выделенный self-hosted runner с KVM либо физическое Android-устройство. Программный режим допускается только как отдельная диагностическая попытка с явно указанным ограничением; не повторять его бесконечно.
5. Перед тестом записывать тип runner, API Android, архитектуру AVD, результат проверки KVM и фактический графический backend.

## 2. Каждый запуск приложения

1. Запустить AVD и дождаться `sys.boot_completed=1` с ограниченным таймаутом.
2. Сохранить `adb devices -l`, `getprop ro.build.version.sdk`, `getprop ro.product.cpu.abi`.
3. Очистить старый журнал и установить APK:
   - `adb logcat -c`
   - `adb install -r <APK>`
4. Запустить именно launcher Activity пакета `ru.aeroclub.informer.mobile`.
5. Не считать запуск успешным по одному только exit code команды `monkey`. Проверить:
   - `adb shell dumpsys activity activities` — текущую/резюмированную Activity;
   - `adb shell pidof ru.aeroclub.informer.mobile` — процесс приложения;
   - `adb logcat -d` — FATAL EXCEPTION, AndroidRuntime, ANR и ошибки старта.
6. Ждать появления главного интерфейса ограниченное время, делать несколько снимков экрана по интервалу. Снимок заставки Android или домашнего экрана не является снимком KD PILOT и означает провал проверки интерфейса.
7. После появления интерфейса сохранить скриншот и подтвердить, что на нём действительно экран KD PILOT, а не системный экран.
8. При неудаче сохранить полный logcat, состояние Activity, список процессов и скриншот. Завершать шаг с ошибкой, а не загружать такой результат как успешный UI-тест.

## 3. Артефакты каждого прогона

Сохранять вместе:
- APK и build-info с SHA-256 и commit SHA;
- скриншот фактического экрана приложения;
- logcat;
- сведения о runner/AVD/KVM/GPU;
- результат проверки Activity и процесса.

Имена файлов должны включать номер workflow run или commit SHA, чтобы результаты разных сборок не смешивались.

## 4. Проверка экранов и виджета

Один стартовый скриншот не подтверждает работоспособность остальных экранов. Для каждого реализованного экрана делать отдельный переход, проверку видимого содержимого и скриншот. W01 проверять отдельно: добавить виджет на домашний экран AVD, проверить его отображение и каждое действие. Не отмечать отсутствующий или недоступный экран как проверенный.

## 5. Критерий успеха

Виртуальный запуск считается успешным только если:
- эмулятор загрузился в пределах таймаута;
- APK установлен;
- процесс и launcher Activity KD PILOT запущены;
- главный интерфейс KD PILOT реально отображён и зафиксирован;
- нет необработанного падения или ANR;
- диагностические артефакты сохранены.

Проверка конкретного экрана или действия считается успешной только после отдельного подтверждения этого экрана/действия. Успешная сборка Gradle — отдельный результат, не равный успешному запуску приложения.
