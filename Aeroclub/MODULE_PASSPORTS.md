# Реестр задач и паспорта модулей — «Аэроклуб · информер»

Версия: 2.1  
Ветка: `aeroclub-informer`  
Область: `Aeroclub/`  
Архитектурная карта общих библиотек: [MODULE_ARCHITECTURE.md](MODULE_ARCHITECTURE.md)

## 1. Как читать статусы

- **Частично реализован** — часть кода существует, но хотя бы один критерий приёмки не пройден.
- **Не реализован** — рабочего кода функции нет.
- **Заблокирован** — для реализации нужны внешние решения/доступы (API, провайдер авторизации, Firebase и т. п.).
- **Требует проверки на устройстве** — наличие кода не подтверждает поведение на реальном Android.

Документ фиксирует фактический текущий прототип и целевую декомпозицию. Статусы не повышать по наличию кнопки или класса: нужна проверка кода, сценариев и сборки на конкретном SHA.

## 2. Правила модулей

1. Один модуль — одна основная ответственность и один владелец данных/правил.
2. Не копировать реализацию между экраном, виджетом и админкой.
3. UI вызывает use case/репозиторий, но не хранит бизнес-логику и не читает SharedPreferences напрямую.
4. Повторно используемый код выделять в библиотеки согласно `MODULE_ARCHITECTURE.md`; не создавать пустые модули и библиотеки ради будущего использования.
5. Переезд кода — отдельный проверяемый этап, без массового переписывания и без удаления исходников до проверки потребителей.
6. Демоданные, локальные изменения, открытие системного меню и реальные серверные действия должны различаться в UI и журнале.
7. Любое изменение модели/хранилища требует проверки миграции существующих данных.
8. Для каждого сценария фиксировать результат: успех, отказ, отмена пользователем, отсутствие разрешения, ошибка сети/сервера.
9. Не хранить секреты в репозитории и не журналировать пароли, токены, полные сообщения и ненужные персональные данные.
10. Обновлять этот реестр и README вместе с функциональными изменениями.

## 4. Реальное распределение исходников

- `:core:common`: чистые доменные модели, канонические статусы ответов, единое форматирование метки DEMO и преобразование даты/времени без Android-зависимостей; есть unit-тесты.
- `:core:data`: `LocalFilePreferences` хранит доменные данные в `aeroclub-local-data.json` в приватной папке приложения; миграция копирует старые значения `flight_informer`, сохраняя исходный SharedPreferences. Серверная синхронизация отключена.
- `:core:ui`: общая палитра, скругления и color resources.
- `:core:android`: единый запуск карт/share chooser и обновление виджета без зависимости на `:app`.
- `:feature:notifications`: планировщик локальных напоминаний, receiver и восстановление после перезагрузки.
- `:feature:admin`: AdminActivity и UI разделов; экранные разделы ещё не вынесены по отдельным модулям.
- `:feature:admin-flights`, `:feature:admin-participants`, `:feature:calendar`, `:feature:messages`, `:feature:settings`: отдельные use-case модули, вызываемые из админ-панели.
- `:feature:informer`: MainActivity — превью информера и действия участника.
- `:app`: точки входа и текущие экраны. Разделы админ-панели ещё не вынесены в отдельные feature-модули.

## 5. Подробные паспорта

### UI-01 — Карточка информера
- **Цель:** показать ближайший активный вылет и четыре действия: «Я еду», «Я не еду», «Маршрут», «Telegram/Поделиться».
- **Владелец:** feature:informer; общая модель и правила — LIB-COMMON, чтение данных — LIB-DATA.
- **Вход:** активный Flight, статус Attendance, ClubSettings для значения по умолчанию только при отсутствии места у вылета.
- **Выход:** события ответа, маршрута и подготовки сообщения.
- **Не входит:** собственное хранилище, выбор получателей рассылки, сетевые запросы.
- **Задачи:** состояния «вылет не назначен», неполные данные, локальный ответ, ошибка чтения; единые подписи и форматирование даты; доступность кнопок и масштабирование.
- **Ошибки:** пустые поля, отсутствующий активный вылет, недоступное действие.
- **Приёмка:** нет фиктивных данных, текст не обрезается, действие даёт понятный результат, карточка соответствует утверждённому макету.
- **Текущий статус:** частично реализован; MainActivity содержит превью, требуется проверка на реальном устройстве.

### UI-02 — Экран-превью
- **Цель:** отображать карточку в приложении и обеспечивать переход к админ-панели.
- **Владелец:** feature:informer.
- **Вход/выход:** те же Flight/Attendance и команды, что UI-01.
- **Зависимости:** core:common, core:data, core:ui, core:android, feature:notifications, feature:admin-participants, feature:settings.
- **Запрещено:** собственная копия логики расчёта ответа или независимые ключи хранения.
- **Задачи:** сравнить с виджетом по данным и формату; проверять состояние после возврата из админки; единая обработка ошибок.
- **Приёмка:** превью и виджет используют один источник истины; после изменений показывают одинаковый активный вылет и ответ.
- **Текущий статус:** частично реализован в MainActivity.

### WID-01 — Домашний виджет
- **Цель:** отображать карточку вылета и доступные действия на Android Home Screen.
- **Владелец:** app / Android widget adapter; общие действия через LIB-ANDROID.
- **Вход:** активный Flight, Attendance, параметры оформления.
- **Выход:** RemoteViews и PendingIntent-команды.
- **Зависимости:** AppWidgetManager, репозитории и модели.
- **Задачи:** проверить все размеры/конфигурации, несколько экземпляров, обновление после CRUD/ответа, перезагрузку и устаревшие данные; безопасные PendingIntent; обработать отсутствие активного вылета.
- **Приёмка:** виджет не хранит собственную копию данных; все экземпляры обновляются; после перезапуска нет сброса данных; действия открывают корректные сценарии.
- **Ограничение:** Android RemoteViews имеет отдельные ограничения, поэтому общий UI-код не означает один и тот же XML для экрана и виджета.
- **Текущий статус:** частично реализован в FlightWidgetProvider; требуется реальная проверка.

### ATT-01 — Ответ участника
- **Цель:** записать «еду»/«не еду» для конкретного участника и конкретного вылета.
- **Владелец:** feature:admin-participants; доменные правила — LIB-COMMON; запись — LIB-DATA.
- **Вход:** flightId, participantId, ответ, timestamp, источник команды.
- **Выход:** сохранённый Attendance, пересчитанная сводка, событие обновления виджета.
- **Задачи:** обеспечить идентичность пользователя; заменить временную привязку к локальному ID устройства на авторизованный participantId после подключения AUTH; запретить дубли; определить поведение смены ответа и удалённого вылета.
- **Ошибки:** нет участника/вылета, повтор операции, хранилище недоступно.
- **Приёмка:** повтор меняет существующую запись; счётчики считаются из данных; ответ не приписывается вымышленному участнику.
- **Текущий статус:** локальная запись теперь требует явного выбора существующего участника; информер, виджет и админка используют единые статусы. Авторизованная межустройственная идентичность и серверные ответы отсутствуют.

### FLT-01 — Управление вылетами
- **Цель:** создавать, читать, редактировать, выбирать активный и удалять/архивировать вылеты.
- **Владелец:** feature:admin-flights; модель/правила — LIB-COMMON; хранение — LIB-DATA.
- **Данные:** стабильный flightId, название, ISO-дата yyyy-MM-dd, время, место, статус, отметка черновика/публикации, временные метки.
- **Задачи:** валидация полей и времени; определить архивирование vs удаление; защита от случайного удаления; корректное поведение при удалении активного; публикация должна быть серверной операцией, когда появится API.
- **Ошибки:** невалидная дата, пустое название, дубликат ID, сбой сохранения.
- **Приёмка:** несколько вылетов существуют независимо; ровно один активный либо явно нет активного; календарь/виджет обновляются; миграция старых SharedPreferences проверена.
- **Текущий статус:** частично реализован через Flight/FlightRepository; отметка «опубликовано» пока локальная и не означает рассылку.

### PAR-01 — Участники
- **Цель:** хранить локальный/серверный список участников и показывать ответы на выбранный вылет.
- **Владелец:** feature:admin-participants.
- **Вход:** Participant, фильтры, flightId.
- **Выход:** список, статусы, агрегаты, безопасный экспорт.
- **Задачи:** перенести все операции участников из AdminActivity в ParticipantRepository; добавить фильтрацию по статусу/ответу; обработать одинаковые имена без потери ID; сохранить историю ответов при удалении согласно согласованной политике; контактные поля добавлять только после определения правового основания и доступа.
- **Ошибки:** пустое имя, повтор, удаление с историей, отсутствие данных.
- **Приёмка:** CRUD переживает перезапуск; поиск/фильтры корректны; статистика совпадает с реестром; демо-данные отделены.
- **Текущий статус:** локальный CRUD сохранён; миграция старых статусов запускается однократно, чтобы не сканировать участников и вылеты при каждом рендере. Операции Activity ещё требуют дальнейшего переноса в единый слой.

### CAL-01 — Календарь
- **Цель:** показывать сохранённые вылеты по полной дате и открывать выбранное событие.
- **Владелец:** feature:calendar.
- **Вход:** FlightRepository и выбранная ISO-дата.
- **Выход:** список реальных событий дня.
- **Задачи:** пустой день; одинаковые числа разных месяцев/лет; смена месяца/года; локаль и часовой пояс; переход к редактированию вылета; обновление после изменения/удаления.
- **Приёмка:** дата сравнивается как yyyy-MM-dd; календарь не создаёт фиктивные события.
- **Текущий статус:** выбор даты хранится через CalendarRepository с миграцией старого ключа; проверка крайних дат и UI-тесты ещё требуются.

### MSG-01 — Сообщения
- **Цель:** формировать объявление, хранить шаблоны/черновики/историю и передавать текст выбранному каналу.
- **Владелец:** feature:messages; общий formatter и Android chooser — LIB-ANDROID / LIB-COMMON по границам.
- **Вход:** шаблон, текст, flightId, целевая аудитория, канал.
- **Выход:** черновик/запись попытки и фактический результат канала.
- **Задачи:** вынести формирование текста из Activity в один formatter; определить статусы draft/prepared/handed-off/delivered/failed; не путать открытие chooser с отправкой; выбрать серверный канал массовой рассылки; реализовать повторы и отчёт частичной доставки после API.
- **Ошибки:** отмена chooser, приложение отсутствует, канал отказал, частичная доставка.
- **Приёмка:** история правдиво отображает этап; отправка не отмечается успешной без подтверждения канала.
- **Текущий статус:** частично реализован через MessageRepository; массовая доставка отсутствует.

### SET-01 — Настройки клуба
- **Цель:** хранить общие настройки клуба отдельно от конкретного вылета.
- **Владелец:** feature:settings.
- **Вход/выход:** ClubSettings.
- **Задачи:** список допустимых настроек; валидация; различать адрес по умолчанию и адрес вылета; определить владельца настройки при нескольких администраторах; подготовить серверную модель после API.
- **Приёмка:** изменение адреса по умолчанию не переписывает уже сохранённые места вылетов.
- **Текущий статус:** частично реализован через ClubSettingsRepository.

### MAP-01 — Маршрут
- **Цель:** открыть карту с местом встречи из выбранного активного вылета.
- **Владелец:** LIB-ANDROID, вызывается из informer/widget.
- **Вход:** сохранённый адрес или проверенные координаты.
- **Выход:** ACTION_VIEW Intent и результат запуска.
- **Задачи:** единый builder запроса; кодирование адреса; приоритет координат при наличии; обработка отсутствия карт и неверного адреса; не использовать фиктивные координаты.
- **Приёмка:** экран и виджет запускают одинаковый маршрут; ошибка не приводит к crash.
- **Текущий статус:** частично реализован; открывается текстовый geo-запрос, точность адреса не подтверждена.

### SHR-01 — Системное «Поделиться» / Telegram
- **Цель:** передать сформированный текст стороннему приложению через системный Android chooser.
- **Владелец:** LIB-ANDROID; текст формирует MSG-01.
- **Вход:** актуальный Flight и сформированный текст.
- **Выход:** запуск chooser/результат отмены или недоступности.
- **Задачи:** единая реализация для экрана и виджета; актуальный текст; обработка отсутствия обработчика; не заявлять доставку; прямую Telegram-интеграцию делать только отдельным согласованным каналом.
- **Приёмка:** UI сообщает только о факте подготовки/передачи в системное меню, не о доставке.
- **Текущий статус:** частично реализован; используется системный chooser.

### NTF-01A — Локальные напоминания
- **Цель:** напомнить на этом устройстве о будущем вылете за час.
- **Владелец:** feature:notifications.
- **Вход:** Flight, время, разрешения уведомлений.
- **Выход:** AlarmManager alarm и локальное Android notification.
- **Задачи:** проверить разрешение POST_NOTIFICATIONS на Android 13+; точность будильника и fallback без exact alarm; отмену/перепланирование при изменении/удалении/смене активного вылета; перезагрузку; Doze и ограничения TECNO/Android; отсутствие уведомления для прошедшего вылета.
- **Ошибки:** разрешение запрещено, расписание не создано, receiver не запущен.
- **Приёмка:** после CRUD остаётся только актуальное расписание; журнал не сообщает об отправке, если система отклонила постановку.
- **Текущий статус:** частично реализован через FlightReminderScheduler, FlightReminderReceiver и FlightReminderBootReceiver; проверка на реальном устройстве обязательна.

### NTF-01B — FCM push
- **Цель:** отправлять удалённые уведомления на зарегистрированные устройства.
- **Владелец:** integration:api + feature:notifications.
- **Зависимости:** Firebase project/configuration, регистрация токена, серверный отправитель, AUTH/права.
- **Задачи:** выбрать Firebase-проект; хранить токены безопасно на сервере; связывать устройство с аккаунтом; подписки/отписки; отправка только разрешённым получателям; обработка отзыва токена, повторов и ошибок.
- **Приёмка:** push приходит на тестовое устройство от серверного отправителя; отказ и отсутствие конфигурации отображаются честно.
- **Текущий статус:** не реализован; заблокирован отсутствием Firebase-конфигурации и серверного отправителя.

### DATA-01 — Общие модели и репозитории
- **Цель:** обеспечить единый источник истины и совместимость данных.
- **Владелец:** LIB-COMMON и LIB-DATA.
- **Существующие файлы:** Flight/FlightRepository, Participant/ParticipantRepository, AttendanceRepository, MessageRecord/MessageRepository, ClubSettings/ClubSettingsRepository, EventLogRepository, SyncRepository.
- **Задачи:** определить публичные интерфейсы репозиториев; перенести модели в common; убрать прямой доступ UI к SharedPreferences; документировать ключи и миграции; выбрать Room как локальную БД после отдельного этапа; не подключать Room/API в одном недиагностируемом массовом рефакторинге.
- **Ошибки:** несовместимая миграция, частичная запись, повреждённые данные.
- **Приёмка:** обновление поверх старой версии сохраняет данные; у сущности один источник истины; UI не выполняет прямые операции хранения.
- **Текущий статус:** частично реализован; SharedPreferences и репозитории существуют, но границы слоя ещё не везде соблюдены.

### API-01 — Серверное API
- **Цель:** дать нескольким устройствам общий источник данных.
- **Владелец:** integration:api.
- **Зависимости:** решение по хостингу, API-контракт, схема данных и AUTH-01.
- **Задачи:** согласовать сущности/эндпоинты, версии, пагинацию, авторизацию, ограничения частоты, ошибки и миграции; создать тестовое окружение; не помещать секреты в APK/репозиторий.
- **Приёмка:** контракт документирован и проверен; сервер авторизует каждую операцию; ошибки сети/прав обработаны клиентом.
- **Текущий статус:** не реализован / заблокирован выбором серверной инфраструктуры.

### SYNC-01 — Синхронизация
- **Цель:** безопасно синхронизировать вылеты, участников, ответы и сообщения между устройствами.
- **Владелец:** integration:sync.
- **Вход:** локальные операции, серверные версии и подтверждения.
- **Выход:** синхронизированное состояние и отчёт ошибок.
- **Задачи:** определить outbox schema; идемпотентные операции; повтор с backoff; версия записи; политика конфликтов; удалённые удаления/tombstones; офлайн-состояние; подтверждение сервера; запрет бесконечного повторения.
- **Приёмка:** два устройства получают одинаковое состояние; повтор запроса не создаёт дубликаты; офлайн не стирает локальные данные.
- **Текущий статус:** сетевой синхронизации и локального outbox нет; SyncRepository оставлен пустым совместимым фасадом. Данные уже сохранены в общем локальном JSON-файле.

### AUTH-01 — Авторизация и роли
- **Цель:** подтвердить личность пользователя и разрешать действия по роли.
- **Владелец:** integration:auth.
- **Задачи:** согласовать роли (например, участник/администратор); вход/выход, восстановление доступа, срок сессии, отзыв; серверная проверка прав на каждую операцию; безопасное хранение сессии; состояние недоступного сервера.
- **Приёмка:** неавторизованный пользователь не выполняет административную операцию напрямую через API; скрытия кнопок недостаточно.
- **Текущий статус:** не реализован; админ-панель прототипа не защищена и не должна использоваться с реальными конфиденциальными данными.

### SEC-01 — Безопасность и персональные данные
- **Цель:** минимизировать риски до появления реальной базы.
- **Владелец:** cross-cutting; проверки обязательны для всех модулей.
- **Задачи:** классификация данных; минимизация контактных полей; правовое основание/согласие; правила экспорта; защита сессий; запрет секретов в Git; очистка чувствительных данных из журнала; серверная авторизация; политика резервного копирования и удаления.
- **Приёмка:** проверены права чтения/изменения/экспорта; журнал не раскрывает лишние данные; секреты отсутствуют в истории Git.
- **Текущий статус:** правила частично описаны в ТЗ, полноценная модель безопасности отсутствует.

### LOG-01 — Журнал событий и диагностика
- **Цель:** сохранять полезные технические события и ошибки без утечки персональных данных.
- **Владелец:** единый EventLogger контракт; текущий EventLogRepository — реализация.
- **Вход:** модуль, операция, время, результат, код ошибки и безопасный контекст.
- **Выход:** ограниченный журнал диагностики.
- **Задачи:** унифицировать названия событий и уровни; регистрировать ошибки репозиториев/интеграций; отделить пользовательские отмены от ошибок; лимит и безопасная очистка; тестирование переполнения.
- **Приёмка:** последние события помогают восстановить цепочку сбоя; отсутствуют токены, пароли, полные сообщения и лишние персональные данные.
- **Текущий статус:** частично реализован; локальный журнал ограничен 200 событиями, покрытие не полное.

### LIB-01 — Общие библиотеки
- **Цель:** извлечь повторяемые элементы без дублирования реализации.
- **Владелец:** архитектурный слой; спецификация в MODULE_ARCHITECTURE.md.
- **Библиотеки:** `:core:common` — модели/правила/форматы; `:core:data` — контракты и реализации репозиториев; `:core:ui` — повторяемые экранные компоненты/токены; `:core:android` — карта/share/widget refresh и системные адаптеры.
- **Задачи:** сначала определить API; извлекать код по одному слою; сохранить обратную совместимость и ключи; подключать библиотеку минимум к двум реальным потребителям; не пытаться сделать единый View для RemoteViews.
- **Приёмка:** нет дублирующих моделей/правил; модули имеют понятные зависимости; проект собирается после каждого извлечения.
- **Текущий статус:** общие библиотеки, модуль информера, админ-панель и уведомления уже вынесены в реальные Gradle-модули; отдельные UI-модули подразделов админ-панели и внешние интеграции ещё не реализованы.

### QA-01 — Функциональные проверки
- **Цель:** подтверждать сценарии независимо от наличия UI.
- **Владелец:** проектный QA / тесты приложения.
- **Набор сценариев:** пустое состояние; создание/редактирование/удаление вылета; смена активного; ответ/повтор ответа; счётчики; поиск участника; календарь через границу года; отмена chooser; отсутствие приложения карт; запрет уведомлений; перезагрузка; миграция старых данных; отсутствие сети; отказ доступа после внедрения AUTH.
- **Приёмка:** каждый тест имеет ожидаемый результат и статус; критические сценарии повторяются на реальном Android; ошибки исправлены, а не скрыты.
- **Текущий статус:** частично реализован; требуется систематизированный тест-план и автоматизация доступных сценариев.

### BUILD-01 — CI и APK
- **Цель:** получать воспроизводимый APK из проверенного коммита.
- **Владелец:** app / GitHub Actions.
- **Задачи:** workflow собирает только проект Aeroclub; проверить JDK/Gradle/SDK; собирать на push/PR в ветку проекта; запускать тесты; загружать APK с ясным именем; сохранять лог; подтверждать commit SHA запуска и артефакта.
- **Приёмка:** workflow успешен для актуального SHA, APK присутствует и скачивается; в репозитории нет секретов.
- **Текущий статус:** частично реализован; существование workflow само по себе не подтверждает успех каждого нового коммита.

## 6. Порядок реализации

1. **Стабилизация прототипа:** исправить расхождения паспортов с кодом, проверить сборку, зафиксировать базовый SHA.
2. **Границы данных:** убрать прямое чтение/запись данных из Activity; унифицировать репозитории и тесты миграции.
3. **LIB-COMMON:** вынести модели, статусы, валидацию и правила без изменения поведения.
4. **LIB-ANDROID:** унифицировать маршрут, share chooser и обновление виджета.
5. **LIB-UI:** извлечь общие токены и повторяемые компоненты экранов; отдельно адаптировать RemoteViews.
6. **Feature-разделение:** по одному отделять информер, вылеты, участников/ответы, календарь, сообщения, настройки и уведомления.
7. **Серверный этап:** сначала API и AUTH, затем SYNC, и только после этого FCM/массовая доставка.
8. **Выпуск:** после каждого этапа — тесты, GitHub Actions, проверка APK и обновление паспортов.

## 7. Защита от зависаний и повторных запусков

- Инициализация репозитория не должна вызывать сама себя напрямую или через цепочку взаимных вызовов. Миграции выполняются однократно с устойчивым маркером.
- Ни одна задача/служба не запускает собственную копию при повторном `onCreate`, `onReceive` или обновлении виджета; для расписаний используются стабильные идентификаторы и операции cancel/reschedule.
- Запрещены бесконечные циклы повторов и немедленные повторы при сетевой/системной ошибке. После появления API повторы должны иметь лимит, backoff, jitter и уникальный operation ID.
- Циклы по данным работают только по конечным коллекциям; перед добавлением фонового worker требуется проверить, нет ли уже действующего эквивалента.
- Тяжёлые миграции не выполняются при каждом `getAll()`/рендере. Синхронизированные методы не должны образовывать обратные блокировки между репозиториями.
- **Приёмка:** повторный запуск экрана/виджета не увеличивает число workers/alarms, не запускает повторную миграцию и не блокирует UI.

## 5A. Паспорта фактически выделенных use-case модулей

### :feature:admin-flights
- **Назначение:** единая оркестрация создания, изменения, выбора активного вылета, локальной отметки публикации и удаления.
- **Входы:** Context и идентификатор/поля вылета; даты принимаются через ISO-валидатор, время — через общий валидатор.
- **Выходы:** созданный Flight либо boolean-результат операции; сообщения об ошибках остаются на уровне UI.
- **Зависимости:** core:common, core:data, feature:notifications.
- **Данные и события:** FlightRepository — владелец записи; LocalFilePreferences сохраняет локальные данные; EventLogRepository фиксирует исход; планировщик создаёт/отменяет локальные напоминания.
- **Ограничения:** публикация и выбор активного вылета не подтверждаются сервером; демонстрационные записи не отправляются в очередь как реальные.
- **Ошибки:** неверная дата/время, отсутствующий вылет, попытка удалить последний вылет, отключённые уведомления.
- **Проверки:** создать/изменить вылет; отклонить неверное время; удалить неактивный/активный вылет; запретить удаление последнего; проверить перепланирование напоминания.
- **Статус:** use cases реализованы; автоматические тесты orchestration и проверка на устройстве ещё не выполнены.

### :feature:admin-participants
- **Назначение:** единая валидация CRUD участников и записи ответа участника.
- **Входы:** имя/ID участника, ID активного вылета, один из трёх канонических статусов.
- **Выходы:** Participant либо boolean-результат; ошибки пустого/повторяющегося имени, отсутствующего ID или неверного статуса отклоняются.
- **Зависимости:** core:common, core:data.
- **Данные и события:** ParticipantRepository и AttendanceRepository — единственные владельцы хранения; EventLogRepository фиксирует результат без имён и текста сообщений.
- **Ограничения:** участники и ответы локальны; реальные контактные данные и серверные права не подключены.
- **Проверки:** добавить/переименовать/удалить; проверить дубликат имени; удалить выбранного участника; записать каждый статус; проверить виджет после изменения.
- **Статус:** use cases реализованы; автоматические тесты с Android-хранилищем ещё не выполнены.

### :feature:calendar
- **Назначение:** единый выбор даты и поиск вылетов на выбранную дату.
- **Входы:** ISO-дата yyyy-MM-dd.
- **Выходы:** canonical ISO string, boolean при выборе даты и список Flight без создания фиктивных записей.
- **Зависимости:** core:common, core:data.
- **Данные и ошибки:** CalendarRepository сохраняет выбранную дату; некорректный ISO отклоняется, фильтр возвращает пустой список.
- **Проверки:** дата с несколькими вылетами, пустая дата, неверный ISO, смена года, удаление вылета после выбора даты.
- **Статус:** use cases реализованы; отдельные unit-тесты и проверка часовых поясов ещё не выполнены.

### :feature:messages
- **Назначение:** единое построение локальных шаблонов текста с именем клуба; метку DEMO берёт из core:common.
- **Входы:** Flight, индекс шаблона и имя клуба.
- **Выходы:** текст сообщения; неизвестный шаблон или отсутствующий Flight возвращает пустую строку.
- **Зависимости:** core:common, core:data.
- **Данные и ограничения:** модуль не отправляет сообщения и не объявляет доставку; сохранение черновиков/истории принадлежит MessageRepository.
- **Проверки:** есть unit-тесты на метку DEMO, данные вылета, имя клуба, неизвестный шаблон и отсутствующий Flight.
- **Статус:** локальные шаблоны реализованы; получатели, массовая рассылка и подтверждение доставки заблокированы до выбора канала и сервера.

### :feature:settings
- **Назначение:** чтение и сохранение настроек клуба через единственный репозиторий.
- **Входы:** имя клуба и место встречи по умолчанию.
- **Выходы:** ClubSettings и boolean-результат сохранения.

## 10. Приоритет локальной доводки и статус звуков

Текущий этап — **локальная работоспособность без сервера**. Сначала завершаются и проверяются локальные сценарии; API, авторизация, удалённая синхронизация и FCM остаются отдельными заблокированными этапами и не должны имитироваться.

### NTF-01A — локальные напоминания
- Источник события: сохранённый будущий вылет на устройстве.
- Ожидаемое действие: уведомление за 1 час до вылета с системным звуком, если уведомления разрешены и пользователь не отключил звук канала.
- Обязательные проверки: разрешение Android 13+, звук/вибрация, беззвучный режим и «Не беспокоить», изменение/удаление вылета, прошедшее время, перезагрузка, Doze и ограничения прошивки.
- Текущий статус: **код есть, фактическое поведение и звук на устройстве не подтверждены**.

### MSG-01 — звук при получении сообщения
- Сейчас нет реализованного входящего канала сообщений между устройствами. Локальный черновик или открытие системного Share не является полученным сообщением.
- Поэтому звук «новое входящее сообщение» сейчас **не реализован**. Не создавать ложные уведомления и не воспроизводить звук без реального события.
- На локальном этапе можно добавить звук только для реально возникающего локального события, если оно будет определено отдельным сценарием; звук каждого нажатия не нужен.
- Удалённое получение сообщений и FCM рассматриваются позже, после появления API/серверного отправителя.

### Правило статусов

Для каждой функции отдельно указывать: «не сделано», «код есть, не проверено», «локально проверено» или «заблокировано внешней зависимостью». Наличие Gradle-модуля или паспорта само по себе не означает готовность функции. Сборки запускать на контрольных этапах после завершения связанного блока, а не после каждого изменения.

## 11. Паспорт MSG-02 — локальный файл объявлений

**Модуль:** `:feature:messages`  
**Классы:** `MessageTransport`, `MessageTransportProvider`, `LocalFileMessageTransport`, `LocalTransportMessage`, `LocalMessageFileWatcher`  
**Потребители:** `:feature:admin` пишет объявление; `:feature:informer` читает и отображает его.  
**Назначение:** простой временный канал между админ-панелью и информером внутри одного приложения на одном телефоне. Реальный транспорт позже заменяется через `MessageTransport`.

- **Файл:** приватное хранилище приложения `files/local_message_transport/messages.json`; не публичный Downloads и не общий файл для других приложений/телефонов.
- **Администратор:** кнопка «Записать для информера (локальный файл)» записывает текст в файл. Пустой текст не принимается. UI явно сообщает, что запись существует только на этом телефоне.
- **Информер:** показывает последнее объявление из канала `informer-announcements`.
- **Проверка файла:** только пока экран информера на переднем плане; интервал 15 секунд (минимум 5 секунд). Сначала сравниваются время изменения и размер файла, JSON читается только при изменении.
- **Нагрузка:** проверка метаданных и чтение выполняются в одном фоновом потоке; чтения не накладываются друг на друга. При уходе с экрана опрос останавливается; нет постоянной службы, бесконечных повторов или рекурсивных вызовов.
- **Запись:** сначала создаётся и синхронизируется временный файл, затем он атомарно заменяет целевой. Если существующий JSON повреждён или недоступен для чтения, новая запись отклоняется — исходный файл не удаляется.
- **Ограничение истории:** не более 500 записей; при превышении остаются последние 500.
- **Статусы:** `LOCAL_ONLY` означает только локальную запись; `SIMULATED_INCOMING` используется только тестовым методом. Никаких подтверждений доставки на другое устройство нет.
- **Безопасность:** текст хранится в приватном файле приложения; не включать полные сообщения в технический журнал. Не использовать реальные персональные данные в тестах.
- **Единая точка выбора транспорта:** админ-панель и информер получают одну реализацию через `MessageTransportProvider`; потребители не создают `LocalFileMessageTransport` напрямую. При замене транспорта изменяется точка композиции, контракт `MessageTransport` сохраняется.
- **Замена транспорта:** оставить интерфейс `MessageTransport`, внедрить реализацию с API/сервером после согласования авторизации и контракта. UI не должен обращаться к файлу напрямую.
- **Проверки приёмки:** администратор сохраняет объявление; информер отображает его после обнаружения изменения; пустой текст/ошибка записи обрабатываются; файл не читается каждую секунду; после ухода с экрана опрос прекращается; повреждённый файл не затирается; другие телефоны не получают это сообщение.
- **Статус:** единая точка выбора транспорта подключена к админ-панели и информеру; **сборка и проверка на устройстве ещё не подтверждены**.


### NTF-SOUND — Политика системного звука
- **Цель:** единообразно настраивать звук и вибрацию локального напоминания о вылете.
- **Владелец:** `feature:notifications`; единственная реализация — `NotificationSoundPolicy`.
- **Вход:** `Context` и состояние системного канала `aeroclub_flight_reminders`.
- **Выход:** созданный при первом запуске канал с системным звуком уведомления и шаблоном вибрации; диагностическое состояние для журнала.
- **Границы:** не воспроизводит звук напрямую и не обходит настройки Android; уже созданный канал не пересоздаётся и не сбрасывает пользовательские предпочтения. Не является звуком входящего сообщения или FCM push.
- **Ошибки/ограничения:** отсутствие `NotificationManager`, отключённый канал, отключённый звук/вибрация, запрет уведомлений и системный режим «Не беспокоить» могут препятствовать оповещению.
- **Проверки:** первое создание канала; повторный вызов без изменения пользовательских настроек; выключенный пользователем звук; выключенные уведомления; фактическое звучание и вибрация на устройстве.
- **Статус:** код добавлен в ветку; сборка и проверка звука на устройстве не подтверждены.


## 6. Дополнение паспорта DATA-01 — единый локальный файл

- **Канонический путь:** приватная папка Android-приложения, файл `aeroclub-local-data.json`.
- **Владелец:** `LocalFilePreferences` в `:core:data`.
- **Потребители:** FlightRepository, AttendanceRepository, ParticipantRepository, CalendarRepository, ClubSettingsRepository, MessageRepository, EventLogRepository.
- **Миграция:** при отсутствии JSON копируются значения из старого `SharedPreferences` `flight_informer`; исходные значения не удаляются.
- **Запись:** временный файл + flush/fsync + атомарное переименование.
- **Повреждённый файл:** автоматический сброс запрещён; операции записи блокируются, чтобы не уничтожить данные.
- **Сервер:** не требуется для локальных сценариев; `SyncRepository` не ставит операции в очередь.
- **Ограничение:** файл приватный, не лежит в публичном `Download` и не синхронизирует другие телефоны.
- **Приёмка:** миграция старых данных, создание/редактирование/удаление, ответы, календарь, настройки, история, виджет и восстановление после перезапуска проверены на одном устройстве.
- **Статус:** код добавлен; приёмка не подтверждена до контрольной сборки и запуска на Android.
