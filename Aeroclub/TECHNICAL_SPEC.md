# Техническое задание — «Аэроклуб · информер»

Версия документа: 1.0  
Проект: `Aeroclub/`  
Рабочая ветка: `aeroclub-informer`  
Статус: базовое ТЗ для прототипа и дальнейшей разработки.

## 1. Цель

Android-приложение с календарём мероприятий для информирования участников аэроклуба о ближайшем вылете, сбора ответов, просмотра участников и подготовки сообщений. Интерфейс администратора предназначен для управления данными клуба. Прототип не должен выдавать локальные демонстрационные данные за реальные общие данные клуба.

## 2. Обязательные правила проекта

0. Перед изменением читать `TASK_REGISTRY.md`, `SCREEN_MAP.md` и актуальную секцию `WORKLOG.md`. Все новые дефекты сначала вносить в реестр; работать сверху вниз по приоритету. Каждому экрану присваивать постоянный ID из `SCREEN_MAP.md` и использовать его в отчётах/коммитах.

1. Работать только в проекте `Aeroclub/` и ветке `aeroclub-informer`. Не изменять PMCA, GPTSenderTest, CoordinateGridAndroid и другие проекты.
2. Не менять основную ветку и не объединять изменения без отдельного решения.
3. Соблюдать утверждённый макет информера: светлая белая карточка со скруглением, спокойные синие/тёмно-синие акценты, стандартные Android-компоненты. Основные элементы: «АЭРОКЛУБ • БЛИЖАЙШИЙ ВЫЛЕТ», название, дата/время, место встречи, статус и действия «Я еду», «Я не еду», «Маршрут», «Telegram».
4. Не добавлять самовольно новые пользовательские экраны, декоративные эффекты или функции вне ТЗ. Административные экраны допускаются только в рамках перечисленных ниже разделов.
5. Главный экран — календарь мероприятий. Даты с мероприятиями выделяются красным; нажатие на красную дату открывает карточку именно этого мероприятия с действиями «Я поеду», «Я не поеду», «Маршрут», «Telegram».
6. Каждый модуль должен иметь паспорт: назначение, границы ответственности, входы/выходы, данные, зависимости, события, ошибки, ограничения, тесты и статус готовности.
7. Один модуль — одна основная ответственность. Не дублировать одну бизнес-функцию в нескольких реализациях; общую логику выносить в общий компонент/сервис.
8. UI не должен содержать бизнес-логику хранения и синхронизации. Доступ к данным должен идти через слой репозитория/сервиса. Не смешивать экран, модель данных, сеть и хранилище в одном классе.
9. Любая функция, которая ещё не подключена, должна честно обозначаться как не настроенная/локальная. Запрещено показывать фиктивный успех отправки, push-уведомления, публикации или синхронизации.
10. Демонстрационные записи должны быть явно помечены. Локальные данные одного устройства не являются общей базой участников.
11. Не хранить секреты, пароли, API-ключи или приватные данные в репозитории. Административный доступ должен быть защищён до подключения реальных данных.
12. Изменения в поведении описывать в README и соответствующем паспорте. Изменения архитектуры отражать в этом ТЗ.
13. Не объявлять сборку успешной без результата CI/локальной сборки. Перед завершением проверять сборку, ошибки workflow и итоговый SHA ветки.
14. Сохранять обратную совместимость SharedPreferences при миграции данных либо явно описывать миграцию.
15. Для действий без подходящего приложения показывать понятную ошибку, а не завершать работу аварийно.

## 4. Функциональные требования

### Календарь и карточка мероприятия
- Показывать название вылета, дату, время, место встречи и статус ответа.
- Кнопки «Я поеду» и «Я не поеду» сохраняют ответ для выбранного мероприятия; карточка использует ID выбранного вылета.
- «Маршрут» открывает установленное приложение карт с запросом места встречи; отсутствие приложения обрабатывается.
- «Telegram» на текущем этапе означает системное меню «Поделиться». Прямую отправку в Telegram нельзя обещать без отдельной интеграции.
- После редактирования данных в админ-панели красные даты календаря должны отражать актуальный список мероприятий.

### Вылеты
- Целевое поведение: создавать, просматривать, редактировать, выбирать активный и архивировать/удалять вылеты.
- У каждого вылета должен быть стабильный ID, название, дата в ISO-формате `yyyy-MM-dd`, отображаемая подпись даты, время, место, статус публикации и список ответов.
- Один активный вылет выбирается явно. Нельзя подменять список вылетов одной редактируемой записью.
- До реализации многозаписной модели экран создания не должен изображать создание нового независимого вылета, если фактически меняется текущий.

### Участники
- Хранить ID, отображаемое имя, статус ответа и необходимые контактные данные только при наличии согласованного источника и правового основания.
- Статусы: ожидает ответа, участвует, не участвует; список должен показывать реальные агрегированные количества, рассчитанные из данных.
- Добавление/изменение/удаление участника должно отражаться в хранилище, а не только в UI.
- Демонстрационные записи отделяются от реальных.

### Сообщения
- Составление и предпросмотр текста.
- Текущее системное «Поделиться» не равно массовой рассылке и не гарантирует доставку.
- Целевая массовая рассылка требует сервера/бота или другого согласованного канала, подтверждения отправки, обработки ошибок и истории.

### Календарь
- Выбор даты и просмотр связанных с датой вылетов.
- Сравнение дат выполняется по ISO-формату `yyyy-MM-dd`, а не по локализованной подписи без года.
- Выбранная дата должна соответствовать событиям в модели данных; календарь не должен создавать фиктивное событие.

### Настройки и доступ
- Настройки клуба отделены от данных конкретного вылета.
- До появления серверной авторизации раздел администрирования считать демонстрационным и не использовать с конфиденциальными данными.
- Целевые роли и права должны проверяться не только скрытием кнопок в UI, но и сервером.

### Уведомления
- Локальные напоминания планируются на устройстве за 1 час до будущего вылета через AlarmManager.
- Экран различает разрешённые и запрещённые уведомления и предоставляет переход к настройкам приложения.
- Push через FCM требует конфигурации Firebase и серверного отправителя; без них удалённая рассылка не реализована.
- После перезагрузки устройства расписание восстанавливает FlightReminderBootReceiver; проверка на реальном устройстве ещё не выполнена.

## 5. Данные и синхронизация

Текущий обязательный этап — полностью локальная работа на одном устройстве без API, аккаунта и Firebase:
- `LocalFilePreferences` в `:core:data` — единый адаптер локального JSON-хранилища `aeroclub-local-data.json` в приватной папке приложения;
- репозитории `FlightRepository`, `ParticipantRepository`, `AttendanceRepository`, `CalendarRepository`, `MessageRepository`, `ClubSettingsRepository`, `EventLogRepository` читают и изменяют данные через этот адаптер; UI не открывает файл напрямую;
- при первом запуске существующие ключи из старого `SharedPreferences` `flight_informer` копируются в JSON-файл; исходный файл SharedPreferences не удаляется;
- JSON-файл записывается во временный файл и заменяется атомарным переименованием; если файл повреждён или версия формата неизвестна, автоматическая перезапись запрещена;
- история черновиков и действий «Поделиться» остаётся локальной; отдельный файл транспорта сообщений `local_message_transport/messages.json` содержит только локальные объявления/тестовые сообщения и не означает удалённую доставку;
- журнал ограничен последними 200 событиями и не должен включать имена, содержимое сообщений, пароли или токены;
- `SyncRepository` — совместимый фасад; серверная очередь отключена и не накапливает фиктивные операции;
- источник истины на локальном этапе — JSON-файл на устройстве; календарь и все экраны читают данные через общие репозитории;
- серверное API, авторизация, удалённая синхронизация и FCM остаются отдельными будущими функциями и не блокируют локальные сценарии.

## 6. Нефункциональные требования

- Нативный Android, понятные подписи, доступные области нажатия, прокрутка на небольших экранах.
- Не допускать перекрытия кнопок, обрезки ключевой информации и потери состояния при пересоздании экрана.
- Обрабатывать пустые значения, неверные даты, отсутствие карт/приложений отправки и ошибки хранения.
- Не запрашивать лишние разрешения.
- Логи не должны содержать пароли, токены и избыточные персональные данные.
- Сборка должна выполняться через GitHub Actions; артефакт и SHA должны относиться к проверяемой версии ветки.

## 7. Критерии приёмки

1. Главный экран открывает календарь; красная дата открывает карточку мероприятия с четырьмя действиями.
2. Ответы сохраняются и отображаются после перезапуска.
3. Изменения вылета отражаются в календаре и карточке мероприятия.
4. Каждая кнопка выполняет заявленное действие либо честно показывает ограничение.
5. Демоданные помечены, массовая отправка и push не имитируются.
6. Нет функций создания/удаления, которые визуально обещаны, но фактически не работают.
7. Для каждого модуля есть паспорт и проверяемые тест-кейсы.
8. CI завершился успешно для актуального SHA; APK создан и опубликован как артефакт.
9. Известные ограничения и незавершённые пункты перечислены в README и реестре модулей.

## 9. Модульная архитектура и общие библиотеки

Подробное распределение ответственности и план выделения библиотек описаны в `MODULE_ARCHITECTURE.md`; полный список задач и паспорта — в `MODULE_PASSPORTS.md`.

Целевая архитектура включает:
- `:core:common` — модели, статусы, правила, валидация и независимые от Android типы результата;
- `:core:data` — контракты репозиториев, локальное хранилище, миграции и единая точка доступа к данным;
- `:core:ui` — повторяемые экранные компоненты, цвета, типографика, отступы и состояния UI;
- `:core:android` — общие адаптеры карт, системного «Поделиться», обновления календаря и Android-уведомлений;
- feature-модули для информера, вылетов, участников/ответов, календаря, сообщений, настроек и уведомлений;
- integration-модули API, авторизации и синхронизации — после согласования внешней инфраструктуры.

**Текущее состояние:** созданы реальные модули `:core:common`, `:core:data`, `:core:ui`, `:core:android`, `:feature:notifications`, `:feature:admin-flights`, `:feature:admin-participants`, `:feature:calendar`, `:feature:messages`, `:feature:settings`, `:feature:admin` и `:feature:informer`; `:app` содержит провайдер календарьа и Android-манифест. Общие модели и репозитории перенесены без изменения package namespace и ключей SharedPreferences. Use-case модули для вылетов, участников, календаря, сообщений и настроек созданы; отдельные UI-модули подразделов админ-панели, серверный API, авторизация, FCM и подтверждаемая синхронизация пока не реализованы. Актуальная сборка после переноса ещё не подтверждена.

### Правило повторного использования

Каждая модель и бизнес-правило имеют одного владельца. Данные календаря, карточки мероприятия и админки берутся из общего слоя. Маршрут, системный chooser, форматирование дат, построение текста сообщения, журналирование и обновление календаря не реализуется повторно в каждом экране. Домашний экранный виджет удалён; повторное добавление RemoteViews/AppWidgetProvider не входит в текущую архитектуру.

### Поэтапная миграция

1. Зафиксировать успешную сборку и базовый SHA.
2. Вынести чистые модели и правила в `:core:common`.
3. Установить единые контракты репозиториев и вынести слой данных в `:core:data`.
4. Вынести повторяемые Android-операции в `:core:android`.
5. Вынести общие экранные компоненты и дизайн-токены в `:core:ui`.
6. Разделять feature-модули по одному, после каждого этапа запускать тесты и CI.
7. Подключать API, AUTH, SYNC и FCM только после согласования серверной инфраструктуры и требований безопасности.


## 10. Звуки, вибрация и звуковые уведомления

1. Звуковые события должны быть перечислены в паспорте уведомлений; нельзя добавлять случайные звуки на каждое нажатие или декоративные звуковые эффекты вне утверждённого поведения.
2. Для локального напоминания о вылете используется системный механизм уведомлений Android и настраиваемый пользователем звук notification channel. По умолчанию не требуется отдельная музыкальная/звуковая библиотека.
3. Канал уведомлений имеет стабильный ID, понятные имя и описание. После создания канала приложение не должно обещать программно изменить звук, если настройки канала уже контролируются Android/пользователем.
4. Учитывать разрешение POST_NOTIFICATIONS на Android 13+, системную громкость, беззвучный режим, вибрацию, «Не беспокоить» и ограничения энергосбережения. Приложение не должно обходить настройки пользователя.
5. Напоминание планируется на час раньше будущего вылета. Изменение даты/времени, активация другого вылета, архивирование/удаление и отмена вылета должны отменять устаревшее расписание и пересоздавать только актуальное.
6. Для прошедшего времени напоминание не ставится. Запрещены бесконечные повторы, рекурсивные запуски, несколько одинаковых alarm/notification и блокирование UI.
7. После перезагрузки расписание восстанавливается безопасно. Ошибки разрешения или планирования должны быть честно отражены в состоянии/журнале.
8. Звук push-уведомления и удалённая рассылка не считаются реализованными до настройки Firebase и серверного отправителя.
9. На реальном устройстве проверяются звук, вибрация, запрет уведомлений, Doze и ограничения прошивки производителя. Наличие кода без проверки не означает приёмку.

## 11. Обязательная последовательность реализации

Полный поэтапный чек-лист от сверки кода и общих моделей до звуков, FCM, тестирования и выпуска ведётся в MODULE_PASSPORTS.md, раздел 9. Порядок обязателен: сначала безопасность архитектуры и данные, затем пользовательские сценарии, после этого системные действия/календарь/уведомления, и лишь после согласования внешних зависимостей — API, авторизация, синхронизация и FCM. Не запускать постоянные сборки после каждого мелкого изменения: собирать на контрольных этапах и всегда проверять точный SHA.

## 12. Приоритет текущего этапа: полностью локальная работа

До отдельного решения о сервере все реализуемые пользовательские сценарии должны работать на одном устройстве без API, аккаунта, Firebase и сети. В первую очередь доводятся локальные CRUD вылетов, участники и ответы, календарь, черновики/история сообщений, настройки клуба, календарь/карточка мероприятия, маршрут/Share, журнал и локальные напоминания. Данные сохраняются после закрытия и перезапуска приложения.

- Локально созданный текст сообщения или запись в истории не является входящим сообщением от другого пользователя.
- Звук при получении удалённого сообщения сейчас **не реализован**: нет работающего канала входящих сообщений, сервера/API или FCM. Нельзя показывать фиктивное получение или воспроизводить звук как будто сообщение пришло.
- На локальном этапе реализуется и проверяется звук системного уведомления для напоминания о вылете. Для локального события «новое сообщение» звук допустим только после появления реального локального источника такого события и отдельного сценария; без события звук не воспроизводить.
- FCM, серверная рассылка, удалённая синхронизация и авторизация не входят в текущий этап локальной доводки. Их паспорта сохраняются со статусом «не реализовано/заблокировано» и не должны задерживать завершение локальных функций.
- Не запускать постоянные сборки после каждого изменения. Сначала закончить связанный блок функций и тестов, затем запускать контрольные тесты/сборку; сборка не считается подтверждённой без результата для актуального SHA.


## 13. Реализация локального файлового режима

- Канонический файл данных: `files/aeroclub-local-data.json` внутри приватной директории Android-приложения.
- Формат: JSON-объект с `formatVersion` и объектом `data`; значения сохраняют типы String/Boolean/Number/Set<String>.
- Публичная точка доступа: `LocalFilePreferences.get(Context)`; репозитории сохраняют прежние ключи и API SharedPreferences, чтобы миграция была точечной.
- Первичная миграция копирует все значения `flight_informer`; старый источник сохраняется для безопасного отката. Файл не является общей базой других устройств.
- Запись сохраняет JSON во временный файл, выполняет flush/fsync и атомарную замену. `apply()` ставит запись в единственную последовательную фоновую очередь с версионированием, чтобы старый снимок не перезаписал новый; `commit()` сохраняет синхронно. Ошибка чтения не должна молча обнулять данные.
- Сборка после каждого мелкого изменения не запускается. Сначала завершается связанный блок локальных сценариев и статическая проверка изменений; затем выполняется одна контрольная сборка/тесты для итогового SHA.
- До контрольной сборки нельзя объявлять этот механизм проверенным на устройстве; необходимо проверить миграцию старых данных, создание/редактирование вылета, ответы, перезапуск, календарь и восстановление после ошибки записи.
