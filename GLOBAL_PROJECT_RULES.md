# Глобальные правила Android-проектов: журналы, Downloads и передача в ChatGPT

Эти правила обязательны для ВСЕХ Android-проектов в репозитории и для новых Android-проектов. Прочитать перед изменением логирования, хранения файлов, экспорта или разрешений.

## 1. Где хранить журнал

- Журнал отладки и технических операций должен быть доступен в публичной папке Android `Download/`, а не только в приватной директории приложения.
- Использовать Android MediaStore для создания/обновления файлов в Downloads на Android 10+; не запрашивать широкое разрешение на всё хранилище без необходимости.
- Для старых Android обеспечить корректный механизм доступа к Downloads (разрешение с runtime-запросом или системный SAF-пикер). Не утверждать, что доступ есть, пока путь записи не проверен.
- При невозможности записи в Downloads явно записать/показать ошибку и сохранить внутреннюю резервную копию; не сообщать об успешной записи без проверки результата.
- Установка/переустановка приложения не должна незаметно удалять пользовательский журнал в Downloads.

## 2. Имя файла

Имя должно однозначно называть проект и назначение, чтобы ИИ мог найти его без догадок. Рекомендуемый шаблон:

`<ProjectName>_<ComponentOrPurpose>_debug.log`

Примеры:
- `Aeroclub_Informer_debug.log`
- `Vario_Synthesizer_debug.log`
- `PMCA_debug.log`
- `GPTSenderTest_debug.log`

Не использовать для основного файла неоднозначное имя вроде `log.txt` или `module-debug.log`. Внутренние резервные файлы могут иметь технические имена.

## 3. Жёсткий предел размера для отправки в ChatGPT

- Полный файл, предназначенный для вставки/отправки в ChatGPT, ограничивать **80 000 символами** (консервативный проектный предел; действительный лимит интерфейса может меняться).
- Ограничение проверять по символам, а не только по байтам. Для UTF-8 символы и байты не равны.
- По достижении предела использовать контролируемую ротацию/удаление самых старых записей; никогда не допускать бесконечного роста.
- При экспорте/копировании повторно ограничивать снимок до 80 000 символов, предпочтительно по границе строки, чтобы не обрезать JSONL-событие.
- Если нужен более длинный архив, разделять его на пронумерованные части, каждая не более 80 000 символов, и сообщать пользователю количество частей. Не отправлять один сверхлимитный текст.
- Не логировать токены, пароли, ключи API, полные сообщения или ненужные персональные данные.

## 4. Контракт логгера

- Фиксировать время, понятный ID проекта, модуль, действие, исход (успех/ошибка/отмена/пропуск) и короткую диагностическую деталь; длительные операции дополнительно содержат длительность.
- Все операции записи должны иметь явный результат. Если запись в Downloads не удалась, не маскировать это как успех.
- Не плодить отдельные дублирующие логгеры: использовать единый проектный модуль/адаптер логирования.
- Перед выпуском проверить: создание файла в Downloads, повторное открытие/добавление, ротацию, ограничение символов, чтение и ручную передачу файла.
- Успешная CI-сборка не доказывает доступ к Downloads на физическом устройстве; статусы «код реализован», «CI прошёл» и «проверено на телефоне» разделять.

## 5. Доступ к Downloads — обязательное требование

Любое приложение, которому по ТЗ нужно создавать или читать файлы в Downloads, должно реализовать минимально необходимый доступ и проверить его на реальном устройстве. На Android 10+ предпочитать MediaStore или SAF; не использовать широкое файловое разрешение как обход Scoped Storage. В интерфейсе ясно сообщать, если доступ отклонён или запись не удалась.

Эти правила являются постоянным стандартом проекта, а не разовым требованием только Aeroclub.


## 6. Реестр задач и нумерация экранов — обязательный стандарт

- У каждого проекта должен быть отдельный `TASK_REGISTRY.md` (или файл с названием проекта + `TASK_REGISTRY.md`) и `SCREEN_MAP.md`.
- Перед работой ИИ сначала читает реестр задач и журнал проекта, сверяет ветку/HEAD и продолжает с верхней незакрытой задачи.
- Новые дефекты сначала заносятся в реестр, блокирующие дефекты ставятся наверх. Каждая задача получает постоянный ID, приоритет, статус, критерии приёмки и сведения о проверке.
- Каждый экран и значимое состояние получают постоянный ID; виджеты используют отдельный префикс, например `W01`. ID не переиспользовать.
- Отчёты и коммиты связывают изменения с ID задач и экранов. Закрытые задачи не удалять.
- CI, unit-тесты, проверка APK и испытание на физическом устройстве являются разными критериями.
