# PMCA: единая платформа и изолированные приложения

Этот документ — обязательный архитектурный контракт для новых функций, модулей и приложений в репозитории AndroidProjects.

## Обязательная проверка правил перед разработкой

До планирования и изменения кода ИИ/разработчик обязан прочитать актуальные версии `README.md`, `docs/PROJECT_RULES.md`, `docs/MODULE_DEVELOPMENT.md`, `docs/PMCA_SHARED_PLATFORM_RULES.md`, `docs/PMCA_LOGGING_CONTRACT.md`, `PMCA/ARCHITECTURE.md`, `PMCA/PROJECT_CONTRACT.md`, а также документацию, паспорт, исходники, тесты и конфигурацию целевого приложения/модуля и связанные GitHub Actions. Для Android-приложений дополнительно проверяются `applicationId`, `namespace`, версии, подпись и workflow APK.

После чтения нужно найти существующие реализации и точки их использования, записать краткий итог проверки и план тестирования. Если файл недоступен, нельзя заявлять, что проверка правил завершена. Нельзя начинать реализацию до завершения этого этапа. Правило обязательно и для ИИ-агента, создающего модуль или приложение.

## 1. Цель

Общие ресурсы PMCA реализуются один раз и переиспользуются. Каждое конечное приложение хранит только свою логику, настройки и артефакты сборки. Нельзя копировать целый старый проект ради одной функции.

## 2. Целевая структура

Это целевая структура; новые каталоги вводятся поэтапно после аудита, без массового перемещения непроверенного кода.

- `PMCA-Core/`: общие API и контракты, реестр, маршрутизация, защита от дубликатов, контроль выполнения, очередь, логирование и общие ресурсы.
- `PMCA-Modules/<module-id>/`: переиспользуемые модули с паспортом, кодом, тестами и документацией.
- `PMCA-Adapters/<adapter-id>/`: интеграция общего API с конкретным приложением или внешней системой.
- `Applications/<app-id>/`: конечные Android-приложения, их интерфейс, разрешения, конфигурация и сборка.
- `tools/`: проверяющие и тестовые инструменты.
- `docs/`: архитектура и стандарты.
- `.github/workflows/`: автоматические проверки и сборки.

Существующие каталоги не удалять и не перемещать вслепую. Сначала составить карту исходников, зависимостей, ресурсов и сборок, затем переносить небольшими проверяемыми шагами.

## 3. Правило единственного владельца

У каждого общего ресурса должна быть одна каноническая реализация и один ответственный модуль. Приложения и адаптеры используют её через стабильный API, а не копируют исходники.

Перед созданием функции:
1. Найти существующую реализацию.
2. Проверить возможность её повторного использования или безопасного расширения.
3. Создавать новую реализацию только при обоснованной необходимости.
4. Зафиксировать владельца, API, зависимости, ограничения и тесты.

Не создавать параллельные реализации одной функции без документированной причины и плана миграции. Это же правило относится к логгерам, службам, демонам, обработчикам событий и механизмам дедупликации.

## 4. Границы ответственности

- Core содержит платформенные контракты и действительно общую инфраструктуру, не координаты конкретного экрана.
- Переиспользуемый модуль выполняет одну определённую способность и не должен зависеть от деталей конкретного приложения без адаптера.
- Адаптер хранит интеграционную логику и особенности целевого приложения.
- Приложение хранит свой package/application ID, UI, разрешения, настройки, брендинг и конфигурацию сборки.
- Координаты, селекторы и особенности интерфейса конкретного приложения нельзя жёстко зашивать в общий модуль. По возможности предпочтительны семантическое обнаружение и Accessibility API; координаты должны быть конфигурацией адаптера, если они неизбежны.

## 5. Контракт модуля

Каждый модуль должен иметь:
- уникальный стабильный ID;
- паспорт `module.json`;
- версию модуля и совместимую версию API PMCA;
- явные машинно-читаемые зависимости;
- определённую точку входа и публичный API;
- тесты успешных, ошибочных и повторных вызовов;
- документацию по назначению, ограничениям и запуску тестов;
- журналирование успехов и ошибок согласно `docs/PMCA_LOGGING_CONTRACT.md`.

Зависимости должны быть выражены идентификаторами модулей или артефактов, а не только произвольным текстом, чтобы инструменты могли проверять их автоматически.

## 6. Изоляция приложений и сборок

- Каждое приложение имеет уникальный `applicationId`, собственный каталог конфигурации и независимый APK.
- Имя артефакта должно включать ID приложения и версию/номер сборки; разные приложения не должны перезаписывать один и тот же файл.
- Общий код подключается как библиотека/модуль зависимости, а не копируется в каталог каждого приложения.
- Версии общих библиотек и API фиксируются явно; обновление общей зависимости должно запускать проверки всех затронутых потребителей.
- Секреты не коммитятся. Подпись релизов и публикация отделены от обычных проверок.
- Временные файлы, APK, отчёты и runtime-логи не коммитятся в исходники, если они не являются намеренно версионируемыми тестовыми данными.

## 7. Выполнение, повторные вызовы и циклы

- Для каждой операции определяются владелец, идентификатор/ключ дедупликации, тайм-аут и конечное условие.
- Повторные попытки ограничены числом попыток и временем; бесконечные циклы и неограниченные автоматические повторы запрещены.
- Обратные вызовы и маршрутизация не должны повторно запускать ту же операцию без явного состояния/идентификатора.
- Общие механизмы защиты от дубликатов и контроля выполнения не копируются внутри приложений.
- Циклы зависимостей проверяются автоматически по структурированному графу зависимостей; дополнительно проверяются подозрительные циклические вызовы и рекурсия в коде.

## 8. Обязательные проверки

До слияния изменений:
1. Проверить формат паспортов и уникальность ID.
2. Проверить наличие и совместимость зависимостей.
3. Проверить граф зависимостей на циклы.
4. Запустить модульные тесты изменённых модулей.
5. Запустить интеграционные тесты затронутых приложений.
6. Собрать затронутые APK с раздельными именами артефактов.
7. Проверить отсутствие случайно добавленных сборок, локальных логов, секретов и дублирующих файлов.
8. Проверить соответствие журналирования контракту и фактические результаты CI.

CLI-тестер — первый уровень проверки, а не доказательство полной корректности. Его покрытие и ограничения должны быть задокументированы; успешная проверка паспортов не заменяет компиляцию и тесты.

## 9. Правило безопасной миграции

1. Аудит существующих файлов и связей.
2. Зафиксировать исходное состояние и текущие рабочие сборки.
3. Переносить один модуль за раз.
4. Обновлять импорты и зависимости, не оставляя копию старой реализации активной.
5. Запускать тесты после каждого переноса.
6. Удалять старый код только после подтверждения, что все потребители используют каноническую реализацию и сборки проходят.

## 10. Definition of Done

Изменение готово, если:
- соблюдены границы Core / Module / Adapter / Application;
- нет необоснованных дубликатов;
- зависимости явные и проверяемые;
- есть тесты на штатный и ошибочный сценарий;
- ограничены повторы и исключены очевидные циклы;
- журналирование соответствует logging contract;
- затронутые проверки и сборки успешны;
- APK и отчёты однозначно идентифицируются;
- документация обновлена.
